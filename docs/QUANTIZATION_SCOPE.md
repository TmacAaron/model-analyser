# 量化辅助公式的实际作用域

检查点60修复短节点／模块路径的量化辅助计数错误，数学引擎升为`0.1.0-execution.20`。画布、生效量化表、物理分配、逐步Decode与容量搜索继续使用同一计算核心；公共结果契约没有新增字段。

## 原因与修复

原`quantization.ts`把根`$model`当作长度6的普通节点排序。当实际节点`x`或`block`的路径更短时，根参数反而最后写入符号表，覆盖已经绑定的局部参数。节点重命名就可能改变辅助计数，实际参数记录与分配结果也会不一致。

现在量化复用`scopedNumericSymbols`：先放入数字工作负载字段，再按根、真实祖先到具体调用应用已经解析的数字参数。根的排序位置显式固定在首位；原参数绑定、节点覆盖、量化选择器优先级、packing／alignment及辅助张量算法保持。不同实例和兄弟节点使用各自的实际参数，不能借用另一调用。

旧独立反例的根P为2、实际短节点局部P为3。每份存储有4个BF16元素，payload为8B；局部P个BF16 scales为6B，故正确分配是14B，旧算法得到12B。旧反例采用显式8B读写声明，所以不能把它的流量直接改成分配字节数；当前另用`storage_allocation`访问的固定参考证明，两个14B权重产生28B流量、28B驻留峰值和0.28s理论耗时。

同一规范存储被两个节点使用时，必须按各自作用域求值后再比较格式。局部P3与P5产生不同的辅助格式，现在明确返回`shared_quantization_conflict`；不会用根P2把二者伪装成相同格式。P3与P3仍共享一份14B规范分配，每次访问分别计数，不重复驻留分配。

## 画布显示与独立数值

“生效量化与来源”表对原结果中已绑定的literal辅助公式计数显示`formula → 3 count（原调用已绑定）`。它读取引擎记录，不使用当前默认值补填，不把该计数当作模块峰值、payload或计算吞吐。

| 固定参考 | 独立预期 |
| --- | --- |
| 短节点／深层叶P3，根P2 | 每份8+2×3=14B，两份合计28B |
| 叶不声明P，最近祖先P5 | 每份18B，两份36B |
| 两个默认P3的重复实例 | 四份各14B，总56B；单独覆盖第二实例为P5的专项得到14／14／18／18B |
| 两个兼容读者共享左权重 | 三份规范分配各14B，峰值42B；四次访问共56B |
| 真实第三次Decode | C2／C3／C4绑定到局部P，单份12／14／16B；fixed-context为12／12／12B |
| 容量候选Z2／Z3／Z4绑定局部P | 两份峰值24／28／32B；28B容量下，区间2…4的最大可容纳值为3 |

另有零辅助计数、局部覆盖P7、长短节点重命名、root本身、固定公式修订与ceil、4bit packing／16B对齐、两张物理卡各自打包等专项证明。两卡复制仍各自保留14B分配，内部BF16计算分类不变，不按存储位宽推断加速。

[九份可移植项目账本](../examples/quantization-scope/hand-ledger.json)由`npm run reference:quantization-scope`生成、重新读盘并复算；包含冲突诊断及完整整数容量候选。合成硬件的实际数值字段用于隔离手算：容量4096B（容量反例为28B）、计算1000 operation/s、HBM100B/s；这些不是设备规格或实测性能。

## 版本与历史证据

此修复改变实际数学，不能只改界面或改写旧结果。四份旧`.19`输入／结果／来源／反例分别保留在`examples/quantization-scope/legacy19-*`；另有当前算法对旧反例的独立复算。未量化C01的完整结果逐字段与旧记录比较，仅算法版本改变，输入hash及其余数学／诊断／来源保持；原有MFU／MBU回归也保留。

输入hash描述固定输入，不包含算法版本。查看旧`.19`精确来源报告时，即使hash和数值相同，当前复核器也要求重算，不能用`.20`的依赖解释历史运行。原用户Qwen没有量化覆盖，其项目数据仍需单独核对，不因为修复测试而添加配置或测量。
